# Orphan ("junk") resources in the firmware APK

## Short version

The firmware APK carries **1543 resource files, ~26 MB as stored, that nothing can
ever load** — they are not in `resources.arsc`. apktool dumps them into
`unknown/res/` and puts them straight back into the rebuilt APK.

Deleting `apktool_workspace/modified/oneOS_Hvac/unknown/res` removes all of them.
Nothing else has to change: apktool 3.0.3 keeps no manifest of unknown files
(`apktool.yml` has no `unknownFiles:` section), it simply copies whatever is in
`unknown/` into the APK root.

```bash
tools/find-orphan-resources.sh          # scan and report
tools/find-orphan-resources.sh --apply  # scan, then delete unknown/res
./build_magisk_module.sh
```

Measured on `1.0.20240929G(181)` / versionCode 385:

| | before | after |
|---|---|---|
| rebuilt APK | ~112.7 MB | **86.87 MB** |
| Magisk module zip | — | 72.22 MB |
| `res/` entries in the APK | 3171 | 1628 |
| all of which referenced by `resources.arsc` | 1628 | 1628 |

## Where the 20 MB came from

The previous firmware APK was 80,819,067 bytes; this one is 114,904,070 — **+32.5 MB**.
Comparing the two zip listings entry by entry, the growth is *entirely* these
orphans. Not one asset, drawable, layout or dex byte of the real app grew:

```
entries only in the new APK: 1545  (33.1 MB)
  1531  res/<2-3 chars>.{xml,png,webp,otf,ttf,mp4}   ← orphans
    12  res/color-v23/*, res/color-night-v8/*        ← real, regenerated by aapt2 anyway
     2  META-INF/TESTKEY.{RSA,SF}                    ← our own signature
entries only in the old APK: 2
     2  META-INF/PLATFORM.{RSA,SF}                   ← stock platform signature
```

So this is **not** content for other car models that the manufacturer bundled in.
It is litter from a resource-optimization/repack pass that renamed and re-emitted
resources without dropping the originals. Two things prove it:

- **549 of the 1543 orphans are byte-for-byte (CRC-32) copies of a resource the app
  does use.** The four biggest orphans alone are exact duplicates of all four real
  fonts — 17.9 MB, 68 % of the whole payload:

  | orphan | identical to |
  |---|---|
  | `res/8A.otf` (6.9 MB) | `res/font/alibaba_puhuiti_regular.otf` |
  | `res/Pa.otf` (6.6 MB) | `res/font/alibaba_puhuiti_medium.otf` |
  | `res/Qk.ttf` (2.4 MB) | `res/font/myinghei_18030_m_c.ttf` |
  | `res/kp.ttf` (2.0 MB) | `res/font/myinghei_18030_h_c.ttf` |

  The rest of the duplicates are mostly `res/mipmap-*` and `res/drawable*` images —
  e.g. `res/WK.png` == `res/mipmap-night-mdpi/behind_ac_bg.png`.

- **Some of them are corrupt.** `res/_Q.webp` fails its own CRC-32 on extraction.
  A file the app actually loaded could not survive that.

The remaining ~800 orphans are compiled XML (layouts, colors, animators) with no
identical twin — stale variants from an earlier revision of the same resources.

### Why the list has 1543 entries but `unknown/res/` only holds 1330

The short names collide when case is ignored (`res/AA.xml` vs `res/aa.xml`), and
exactly **213** of the 1543 do. On macOS/APFS, which is case-insensitive by default,
apktool overwrites one with the other while unpacking, so 213 of them never reach
the tree. They are junk either way; the collisions are all *within* the orphan set —
no orphan ever collides with a real resource name.

## How to find them again after a firmware update

**Do not reuse `docs/orphan-resources.txt` as a delete list.** The short names are
assigned by the optimizer per build; the next firmware will use a different set.
Re-derive the list instead — that is what `tools/find-orphan-resources.sh` does:

1. List every `res/…` entry stored in the APK (`unzip -lv`).
2. List every `res/…` path that `resources.arsc` references
   (`aapt2 dump resources <apk>`, lines marked `(file)`).
3. Orphans = (1) − (2). Sanity check: (2) − (1) must be **empty** — a referenced file
   missing from the APK means a broken APK, stop and investigate.
4. `rm -rf apktool_workspace/modified/oneOS_Hvac/unknown/res`.

The script also refuses to delete anything if a file in `unknown/res/` turns out to
be referenced by `resources.arsc`, so it stays safe if a future firmware puts real
resources there.

`docs/orphan-resources.txt` is kept only as the record of what version
`1.0.20240929G(181)` shipped.

### Verifying after the build

```bash
AAPT=~/Library/Android/sdk/build-tools/36.1.0/aapt2
APK=magisk/system/app/oneOS_Hvac/oneOS_Hvac.apk
$AAPT dump resources $APK | grep -oE '\(file\) res/[^ ]+' | sed 's/^(file) //' | sort -u > /tmp/ref
unzip -l $APK | awk 'NF>=4 && $4 ~ /^res\// {print $4}' | sort -u > /tmp/all
diff /tmp/all /tmp/ref && echo "OK: every res/ entry is referenced, nothing is missing"
```

For `1.0.20240929G(181)` this prints `OK` with 1628 entries on both sides.

## What was deliberately *not* deleted

These are large and only used on some cars, but unlike the orphans above they are
reachable from live code, and they were already present in the previous firmware —
they are not part of the size regression. Removing them is a behaviour change, not
a cleanup, so it needs the car's actual configuration to be checked first.

| Path | Size | Used when |
|---|---|---|
| `assets/seat_regulate_kx11a3/` | 25.1 MB | car reports the **KX11A3** seat configuration |
| `assets/seat_regulate/` | 7.1 MB | any other configuration (the default) |
| `assets/lottie/` | 10.3 MB | live-wallpaper animations, light + night |
| `res/font/` | 17.9 MB | 4 CJK fonts; the Latin/Cyrillic glyphs come from these too |

`assets/seat_regulate_a1/` is referenced by the code but **not shipped** — the build
is not the FX11A1 flavour, so that branch is dead.

The seat-animation variant is picked in
`smali/com/geely/hvac/classify/classifyreturn/SeatKeyReturn.smali`:

```
isFX11A1()                          → "seat_regulate_a1/"      (not shipped)
carType == CarType.KX11A3           → "seat_regulate_kx11a3/"
otherwise                           → "seat_regulate/"
```

and `carType` is only ever set to `KX11A3` from
`MainViewModel.intKx11a32Bool(I)` — i.e. when `CommonUtils.isKX11_A2()` (hardcoded
`true` in this build) **and** the vehicle signal equals `0x85` (133). The signal
arrives through a property-change switch that logs it, and the resulting
`mIsKx11A3Mode` is bound into the main climate screen
(`PagerItemAirconditionBindingImpl`), the seat screen and the seat-detail screen.

To find out which variant your car uses, watch for the log line while the app starts:

```bash
su
logcat | grep 'kx11a3, value:'
```

The line is emitted by `MainViewModel` through `LogUtil.i`, so its logcat tag is
`HvacApp:092900:MainViewModel`.

`value: 133` means the car is in KX11A3 mode and `assets/seat_regulate/` (7.1 MB) is
the dead one; any other value means `assets/seat_regulate_kx11a3/` (25.1 MB) is.
Only then is it safe to drop one of them.

`CommonUtils` also shows this APK is the KX11_A2 build flavour — `isKX11_A2()`
returns `true`, `isFX11()`, `isG636()` and `isG733()` all return `false`, so no
other-model branch in the code is live.
